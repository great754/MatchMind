MatchMind explained

A plain-language and technical guide to the current repository, its data, and its analytics.

One-sentence overview: MatchMind takes a panoramic soccer video plus tracking and event files, converts player positions into football-pitch coordinates, estimates movement and possession, detects observable transfers, and writes a review report.

1. The big picture

Simple version

The project has two main jobs. The vision renderer makes a video with a small top-down pitch. The analytics pipeline studies where players and the ball were, then creates CSV files, graphs, and an HTML report.

Detailed version

Video and dataset files-> Load and align data-> Convert coordinates-> Motion-> Possession-> Transfers and shots-> CSV files and report

The tactical video starts at visualize_pitch.py. The analytics report starts at pipeline.py. They share the dataset, but they are not the same output.

2. What are MOT IDs?

Simple version

No. An MOT ID is usually not the number on the player's jersey. It is a label assigned by the tracking system so the computer can say, "this player in frame 20 is the same player as this player in frame 21."

Detailed version

MOT means Multiple Object Tracking. The file has rows like:

frame, id, x, y, width, height, ...

The id value is the track identity. In this match there are 22 tracking IDs, usually numbered 1 through 22. The number does not have to match the player's shirt number.

The analytics report also has a real player ID such as 476371. That is a different identity from the MOT ID. The synchronization file connects them:

real player ID 476371  <-->  MOT track ID 13

The current dataset's player metadata has a back_number field, but load_mot() does not read it and the MOT text file does not contain it. So the current renderer cannot claim that MOT ID 13 means jersey number 13.

3. How does load_mot() work?

Simple version

It opens the tracking text file, gives names to its ten columns, and calculates a point near each player's feet. That foot point is more useful than the box's top-left corner because it represents where the player touches the ground.

Detailed version

load_mot() calls pandas.read_csv() with header=None, because the text file has no header row. It assigns these names:

ColumnMeaning
frameVideo frame number, starting at 0 in this dataset.
player_idMOT tracking identity, not necessarily jersey number.
x, yTop-left corner of the image bounding box.
width, heightSize of the bounding box in pixels.
unused_1 through unused_4Extra MOT fields. They are currently retained but not used.

Then it adds:

foot_x = x + width / 2
foot_y = y + height

That means the foot point is the horizontal center of the box at its bottom edge. The function does not detect players, identify teams, read jersey numbers, or convert image pixels into meters. Those jobs happen elsewhere.

4. How does load_homography() work?

Simple version

It loads a saved 3-by-3 math matrix from a NumPy file and checks that the matrix has the expected shape. It does not calculate the matrix.

Detailed version

load_homography() calls np.load() on the supplied .npy file. It expects a matrix shaped:

[[a, b, c],
 [d, e, f],
 [g, h, i]]

That matrix can map a point from one flat coordinate system to another using homogeneous coordinates:

[x_image, y_image, 1] -> H -> [x_pitch, y_pitch, w]
then divide x_pitch and y_pitch by w

The function verifies H.shape == (3, 3) and returns a floating-point matrix. It does not apply the matrix to points. In the current active code, PitchCoordinateTransformer uses piecewise triangulation instead because the panoramic image has nonlinear distortion. The repository still contains a supplied homography file and this loader as a useful dataset utility.

5. How does PitchCoordinateTransformer work?

Simple version

Imagine stretching a net over the image. The known landmarks are pins in the net. The program makes small triangles between nearby pins. When it sees a player's image position, it finds the triangle containing that point and estimates the matching pitch position from the triangle's three corners.

Detailed version

PitchCoordinateTransformer reads the keypoint JSON. Each entry pairs:

pitch point: (x meters, y meters)
image point: (x pixels, y pixels)

For example, one known point might say that image pixel (2050, 242) corresponds to pitch location (52.5, 34).

  1. All image landmarks are passed to SciPy's Delaunay triangulation.
  2. Delaunay creates triangles whose vertices are the calibration landmarks.
  3. For a player point, find_simplex() finds the triangle containing it.
  4. The code gets the triangle's precomputed transform.
  5. It calculates three barycentric weights. The weights add to 1 and describe how much each triangle corner contributes.
  6. The same weights are applied to the three pitch-coordinate corners.

In simplified math, if the image triangle has corners A, B, and C, a point is represented as:

image_point = w1*A + w2*B + w3*C
where w1 + w2 + w3 = 1

The transformer uses those same weights on the corresponding pitch corners. If the point is outside the triangles' outer boundary, it returns None; the batch method turns that into [NaN, NaN].

The current validation error is nearly zero for the supplied landmarks. That only proves the transformer reproduces its calibration points. It does not prove every location between landmarks is perfectly accurate.

6. Why does the team classifier sample every 50 frames?

Simple version

It does not need to identify the team again every 50 frames. It samples every 50 frames to collect many views of each shirt, then makes one stable team decision for each tracking ID. Sampling only once is faster, but one frame may be blurry, dark, occluded, or show the goalkeeper in a confusing pose.

Detailed version

classify_teams() samples frames 0, 50, 100, and so on. At 25 FPS, that is one sample every 2 seconds.

For each sampled frame it:

  1. Gets every MOT bounding box.
  2. Crops the upper-middle torso area.
  3. Removes likely green grass pixels.
  4. Converts colors to LAB, which is often more stable for color comparison.
  5. Stores a representative color for each tracking ID.
  6. Takes the median color across the whole clip for each player.
  7. Uses KMeans with two clusters to form two teams.

So the code is not constantly changing a player's team. It is gathering repeated evidence before making one stable assignment.

One sample could work if every crop were perfect, but it would be fragile. More samples help with shadows, motion blur, players turning, partial occlusion, and temporary grass contamination. A better implementation could sample fewer carefully chosen frames, but repeated sampling is still useful.

7. What does align_clip.py do?

Simple version

It figures out which moment in the long GSR match timeline corresponds to frame 0 of the short MOT video. It also figures out which real player is which MOT tracking ID and which team each player belongs to.

What are GSR and MOT?

MOT
The short-video tracking file. It says where 22 tracked boxes are in every clip frame, using image pixels and temporary tracking IDs.
GSR
The repository uses GSR as the name for the dataset's long, global scene annotation stream. Its JSON files contain player annotations with image bounding boxes, pitch-coordinate boxes, real player IDs, and team-side attributes. The code does not define an official expansion of the acronym.

The two sources describe the same match, but they use different timelines and different IDs. The GSR files are much larger than the MOT file, which is why align_clip.py can turn them into smaller compact .npz files.

Detailed process

  1. Read GSR annotations. It extracts each player's image foot position, pitch position, real player ID, and team side.
  2. Read MOT frame 0. It gets the 22 MOT foot positions in the first frame of the short clip.
  3. Search both halves. It compares the MOT frame-0 pattern against many possible GSR frames. A good candidate is a GSR frame where the group of player positions looks like the MOT group.
  4. Refine the timing. After finding a rough candidate, it tests nearby offsets and uses checkpoints throughout the 6,000-frame clip.
  5. Associate players. At a checkpoint, the program has two lists of points: GSR player points and MOT player points. It needs to decide which GSR point matches which MOT point.
  6. Save votes. Across many checkpoints, it votes on the most likely real player ID and team side for each MOT ID.

Hungarian matching is the point-association step. It builds a cost matrix where each cost is the pixel distance between one GSR foot point and one MOT foot point. The Hungarian algorithm chooses a one-to-one assignment with the smallest total distance. In other words, it associates each visible MOT track with the most compatible GSR player position, while preventing two MOT players from claiming the same GSR player.

Temporal offset means the starting index in the long GSR timeline. If the offset is 5999, then local MOT frame 0 is compared with GSR frame 5999, local MOT frame 1 with GSR frame 6000, and so on.

The output is 118575_sync.json. It contains the half, offset, real-player/MOT mappings, team sides, and an estimated matching error.

8. Which coordinate source does analytics use?

Simple version

By default, analytics uses the GSR pitch positions. It does not start with the panoramic image and calculate a homography for every player. You can explicitly choose the MOT route, in which case it transforms panoramic image positions using the triangulated pitch calibration.

Detailed version

load_recording() has two modes:

ModeInput player positionsCoordinate conversion
--player-source gsrGSR compact pitch arraysAlready supplied in metric pitch coordinates.
--player-source motMOT bounding boxes in panoramic image pixelsFoot points go through PitchCoordinateTransformer.

The default command uses GSR:

python -m src.analytics.pipeline

The alternative is:

python -m src.analytics.pipeline --player-source mot

GSR is preferred for analytics because its player pitch positions and the ball positions already use a compatible metric coordinate system.

9. Does the ball have x, y, and z?

Simple version

This project uses only the ball's x and y position on the ground plane. It does not know the ball's height. So it can estimate left/right and up/down on the field, but not whether the ball is in the air.

Detailed version

The ball files contain frame information, x, y, and a status value. The loader changes the coordinate origin by adding:

x_pitch = x_ball + 52.5
y_pitch = y_ball + 34

There is no z coordinate in the active ball data. The analytics therefore cannot distinguish a rolling pass from a lofted pass at the same ground position. Ball speed is a 2D ground-plane speed, not a full 3D speed.

When status is unknown, the code sets the ball position to NaN. It does not invent a position for those frames.

11. What are BAS action annotations?

Simple version

BAS annotations are human or dataset-provided labels saying that something happened at a particular time, such as a pass, shot, tackle, header, or cross. MatchMind uses them as reference events and timeline anchors.

Detailed version

The BAS file is the 12-class action annotation JSON. Events include fields such as:

frame
gameTime
position
label
player_id
team

The analytics converts event times into local clip frames. It uses labels such as PASS, HIGH PASS, CROSS, and THROW IN as pass-like reference events. It uses SHOT for shot validation.

Important: BAS labels do not automatically create detected passes or shots. The detectors work from positions and ball motion. BAS events are compared afterward, although the reconstructed ball path also uses BAS anchors, so the comparison is not fully independent.

12. How does motion.py calculate movement?

Simple version

The program compares a player's position from one frame to the next. It divides the distance by the time between frames to get speed. It uses smoothing to reduce noisy jumps and rejects movements that are too fast to be believable.

Detailed version

calculate_motion() receives an array shaped like:

[[x0, y0],
 [x1, y1],
 [x2, y2], ...]

Raw speed: for frame i, it calculates the Euclidean distance from the previous position:

step = sqrt((x[i]-x[i-1])^2 + (y[i]-y[i-1])^2)
raw_speed = step * fps

Median filtering: a short median window replaces an isolated spike with a more typical nearby value. This helps when one tracking box briefly jumps.

Savitzky-Golay smoothing: this fits a small polynomial over a moving window of positions. Unlike a simple average, it can preserve the general shape and slope of movement while reducing noise. The current player window is 15 frames, or about 0.6 seconds at 25 FPS.

Velocity: the change in the smoothed x and y coordinates per second:

vx = (smoothed_x[i] - smoothed_x[i-1]) * fps
vy = (smoothed_y[i] - smoothed_y[i-1]) * fps

Smoothed speed:

speed = sqrt(vx^2 + vy^2)

Distance: accepted step lengths are added over time. Missing gaps and rejected jumps contribute no distance. Therefore the result is measured distance from usable evidence, not guaranteed total distance.

The smoothing is centered, so it uses future frames. This is appropriate for offline analysis but would not be a real-time algorithm.

13. How does possession detection work?

Simple version

The program asks which player is close to the ball, whether the ball is moving slowly enough to be controlled, and whether the same player stays close for several frames. If two players are almost equally close, it refuses to choose and marks the moment contested.

Detailed version

detect_possession() calculates, for every frame:

  • Distance from the ball to every player.
  • Relative speed between the ball and every player.
  • The nearest player.
  • The difference between the nearest and second-nearest distances.

A player becomes a candidate when they are within 2.5 meters and the ball's motion is compatible with control. The candidate must remain valid for five frames before becoming the owner.

An existing owner gets hysteresis: they can remain the owner out to 3.5 meters. This prevents ownership from flickering whenever the distance changes by a tiny amount.

The detector clears ownership when:

  • the ball position is missing
  • the ball leaves the pitch
  • the ball speed is unavailable
  • two nearby players make the situation ambiguous

The output state can be controlled, candidate, free, contested, unknown, or out_of_play.

14. How is a pass detected?

Simple version

A pass is treated as: one player controls the ball, the ball travels independently for a while, and another player later controls it. The code does not simply trust the BAS pass label.

Detailed version

detect_passes() is a small state machine.

  1. Remember the last controlled player.
  2. When control ends, start a pending transfer.
  3. Wait for at least three independent flight frames.
  4. When a new player controls the ball, finish the transfer.
  5. Measure distance, duration, path length, and ball speed.
  6. Call it completed if the receiver is on the same team.
  7. Call it intercepted if the receiver is on the other team.

It rejects short movements, very slow movements, self-recoveries, and transfers across missing data. If nobody receives the ball before a timeout or the end of the recording, the result may be unresolved.

Because the input is approximate and the ball path is reconstructed, these should be called observable transfer candidates, not guaranteed intentional passes.

15. How does validate_events() work?

Simple version

It compares the program's predicted events with reference events. Each reference event can be used only once. A prediction matches when it is close enough in time and, when requested, has the correct actor.

Detailed version

validate_events() builds a cost matrix. Each prediction is compared to each reference:

time_difference = abs(predicted_frame - reference_frame) / fps

If the difference is greater than the tolerance, the pair is made invalid. For pass validation, the sender ID must also equal the reference player ID.

Then it uses a one-to-one assignment algorithm. This matters because two predictions near one reference should not both count as correct.

TermMeaning
True positive / matchedA prediction paired with a reference.
False positiveA prediction with no matching reference.
False negativeA reference event the detector missed.
PrecisionOf the predictions, how many matched.
RecallOf the references, how many were found.
F1A combined balance of precision and recall.

If there are no reference events, precision and recall are null, not 1.0. That is why the current clip's shot validation is shown as unavailable: the clip contains no BAS shots.

16. Mistake: goalkeepers receive the wrong team color

Simple version

The current standard video guesses teams from shirt colors. Goalkeeper shirts are often different from their teammates, so a two-color shirt clustering algorithm can put a goalkeeper into the other team.

What is happening?

The default tactical renderer calls classify_teams(). It clusters all 22 representative jersey colors into exactly two groups. That assumes the two visual color groups are the two teams. It does not understand positions, goalkeeper roles, or team identity.

But the alignment pipeline has better information. GSR annotations include team-side attributes, and align_clip.py writes those team-side mappings into 118575_sync.json. The current renderer already uses that authoritative mapping when --annotations is enabled, but the normal render uses the jersey classifier.

Better approach

  1. Use the GSR team-side mapping as the primary team assignment whenever 118575_sync.json exists.
  2. Use the jersey classifier only as a fallback when no authoritative mapping is available.
  3. Use goalkeeper location and role as a consistency check, not as the main team detector.
  4. For multiple matches, create a calibration table that maps each tracking ID to its authoritative team after alignment.

Jersey color is still useful for naming colors such as blue and red, but it should not decide team membership when a dataset-provided side label is available.

17. Mistake: the homographic view is not accurate enough

Simple version

The problem may not be one single bug. The panoramic camera bends the image, the calibration points may be sparse or imperfect, and a player's box foot point may not be exactly where their real foot touches the field.

What could cause the error?

  • Panorama distortion: one global homography assumes a flat projective camera. A panoramic or fisheye image often violates that assumption.
  • Calibration landmark quality: a landmark that is a few pixels wrong moves nearby estimates.
  • Landmark coverage: interpolation is less trustworthy far from landmarks and unavailable outside the convex hull.
  • Bounding-box foot estimate: x + width/2, y + height is only an approximation. A box may include shadow, grass, or a player leaning.
  • Coordinate conventions: image y increases downward, while pitch y is a chosen field coordinate. Flipped axes or wrong origins create systematic errors.
  • Time alignment: if the video frame and tracking row do not refer to the same moment, a moving player appears in the wrong place.
  • Camera or padding differences: calibration may have been created for a differently cropped or padded image.

Does the dataset already provide a mapping?

Yes, the dataset provides useful mapping ingredients:

  • image-to-pitch keypoints
  • a supplied homography matrix
  • camera intrinsics
  • GSR annotations with image and pitch positions
  • padding metadata

However, the repository still has to choose how to use them. The current code implements the mapping in PitchCoordinateTransformer using piecewise affine triangulation. The supplied global homography is loaded by load_homography(), but the active transformer does not use it because one global matrix is usually too simple for this panoramic view.

What would improve it?

  1. Use GSR pitch positions directly whenever they are available and the goal is analytics accuracy.
  2. Compare transformer output against GSR pitch positions at many known player locations, not only the calibration landmarks.
  3. Report median and 95th-percentile error across the pitch.
  4. Review and correct landmark points, especially near the edges and goal areas.
  5. Use a denser piecewise model or camera-specific calibration if errors vary across the panorama.
  6. Improve foot-point detection instead of always using the bottom-center of the box.
  7. Verify frame alignment before judging the spatial transform.

The near-zero calibration error printed by the current transformer means it reproduces the landmarks it was given. It does not prove that player locations between those landmarks are accurate. The next useful measurement is an independent GSR-versus-MOT error report over many frames and players.

18. Useful commands

# Run the tactical video renderer
python -m src.vision.visualize_pitch

# Run analytics with GSR player positions
python -m src.analytics.pipeline

# Run analytics with MOT plus the triangulated coordinate transform
python -m src.analytics.pipeline --player-source mot

# Rebuild compact GSR files and synchronization metadata
python -m src.vision.align_clip

# Run all tests
python -m unittest discover -s tests -v
Bottom line: MOT tells the project where tracked boxes are in the video. GSR supplies a richer, already-calibrated player representation. The triangulated transformer is the project's fallback for converting panoramic image pixels into pitch meters. Analytics defaults to GSR because it is already in pitch coordinates, and the current team-color mistake comes from using jersey clustering where the aligned GSR team mapping would be more reliable.
