02 / Two ways in

What is MatchMind doing?

Fifth-grade view

Imagine a soccer match made of thousands of snapshots.

The computer follows the players and ball from snapshot to snapshot, draws them on a tiny soccer field, and looks for patterns such as moving fast, being near the ball, or sending the ball to another player.

Technical view

MatchMind is an offline, metric-space reconstruction and event-inference pipeline.

It normalizes multiple annotation timelines into one recording-local frame grid, chooses a coordinate source, computes quality-gated motion, applies heuristic ownership and transfer state machines, then serializes deterministic facts into reports and optional bounded commentary.

What it does not know

A picture can be blurry, and a ball can hide.

It does not truly see the ball's height, know every player's shirt number, or understand a player's intention. It records uncertainty instead of pretending.

What it does not claim

The outputs are estimates, not official match statistics.

Ball height is absent, ball coordinates are event-interpolated, identities are not roster-verified, smoothing is non-causal, and BAS matching is not independent validation.

03 / The raw material

What goes in?

The code treats every source as a different view of the same match. Synchronization is what lets those views talk to each other.

Panoramic video

The big camera view of the match. It is useful for seeing what happened, but the computer needs extra files to measure it.

The clip is decoded with OpenCV and streamed frame by frame. The renderer checks that its FPS, frame count, and zero-based MOT timeline agree.

Used by: tactical renderer, jersey fallback, optional report video.

MOT detections

Boxes around players. The number on a box helps the computer keep following the same person.

Rows contain frame, track ID, image box position, width, height, and unused MOT fields. The foot point is the box center at its bottom edge.

Used by: alignment, calibration fallback, video marker joins.

GSR annotations

A second notebook that already knows more about where players are on the soccer field.

GSR supplies image boxes, pitch-coordinate boxes, actor IDs, and team sides. Compact arrays are preferred to repeatedly parsing huge JSON files.

Used by: primary metric player positions and authoritative team labels.

Ball NPZ files

A list of where the ball was thought to be at each moment.

The ball arrays use a center-circle origin and are translated by (+52.5, +34) into the 105 x 68 m corner-origin pitch frame. Status zero becomes missing data.

Used by: motion, possession, transfer, shot, and report stages.

BAS actions

Helpful labels such as pass or shot that can be compared with the computer's guesses.

BAS annotations use the released-half clock. The loader converts them into clip-local frames using one-based correction and the inferred source offset.

Used for references and windows, never to create detector predictions.

Calibration landmarks

Known dots saying, "this picture spot matches this spot on the real field."

The keypoint file pairs metric pitch coordinates with panoramic image coordinates. Delaunay triangulation and barycentric interpolation provide the active projection.

Used by MOT projection and ball image overlay.

04 / Make the clocks agree

How does synchronization work?

Before calculating anything, the pipeline must know which player and which moment each file is talking about.

Fifth-grade view

Think of two videos that started at different times. The program looks for a moment where the 22 player dots have the same shape in both videos. Once it finds that moment, it keeps checking the match to make sure the dots still line up.

Technical view

align_clip.py compares the MOT frame-zero foot-position pattern against candidate GSR frames in both halves. It evaluates coarse candidates at several offsets, refines the best candidate, then uses Hungarian assignment at 21 checkpoints.

  1. Read MOT foot positions from local frame zero.
  2. Scan both GSR halves for plausible spatial matches.
  3. Compare candidate alignments at multiple offsets.
  4. Refine the offset near the best candidate.
  5. Vote on actor IDs and team sides across checkpoints.

Why the Hungarian algorithm?

If two dots are close, the program still needs each player to get only one matching player. Hungarian matching makes a one-to-one assignment with the smallest total distance.

It builds a cost matrix of image-foot distances between GSR detections and MOT detections. The linear-sum assignment minimizes total cost while preventing two MOT tracks from claiming one GSR actor.

cost[gsr_player, mot_player] = pixel_distance
assignment = argmin(one_to_one_total_cost)

The saved sync sidecar contains the half, zero-based clip offset, actor mapping, team mapping, and alignment error.

05 / From pixels to grass

How does the homographic view work?

The short answer is subtle: the repository has a homography utility, but the active renderer uses a piecewise triangulated mapping instead.

i
Terminology correction

The visual idea is often called a homographic or top-down view. A single global homography is not the active implementation because the panoramic camera has nonlinear distortion. MatchMind uses local triangle mappings built from calibration landmarks.

Fifth-grade view

Imagine stretching a rubber net over the camera picture. The net has pins in places we know. The computer makes little triangles between the pins. If a player is inside one triangle, it uses the three nearby pins to estimate where that player is on the field.

If the player is outside the net, the program says, "I do not know," instead of guessing far away.

Technical view

PitchCoordinateTransformer loads image/pitch keypoints, runs SciPy Delaunay triangulation in image space, finds the containing simplex, and uses the transform's barycentric coordinates to interpolate the corresponding pitch triangle.

p_image = w1*A + w2*B + w3*CThe weights sum to one. The same weights are applied to the corresponding pitch vertices.
w1 + w2 + w3 = 1Outside the calibration convex hull, find_simplex() returns no triangle and the result becomes missing.

Why not one homography?

A single flat ruler cannot perfectly measure a picture taken through a curved, wide camera view. Small local triangles bend the measurement to fit different parts of the picture.

A global 3x3 projective transform assumes one consistent planar relationship. Panoramic/fisheye distortion violates that assumption. Piecewise affine interpolation is a pragmatic local approximation using supplied landmarks.

PathRole
Homography loaderRetained dataset utility; validates a 3x3 matrix.
Delaunay transformActive MOT-to-pitch projection.
GSR pitch coordinatesPrimary analytics/rendering source when present.
GSR-first position selection

For each player/frame pair, the tactical tracker first uses a valid GSR pitch coordinate. Only a missing GSR sample falls back to the calibrated MOT projection. A present but out-of-pitch GSR value is preserved for audit rather than silently replaced.

Each output row records position_source as gsr, pitch_transform, or unavailable.

06 / Motion

How is speed calculated?

Motion begins with position differences, then applies quality controls so one bad detection does not become a fake sprint.

Fifth-grade view

The program asks how far a dot moved between two pictures. Since the pictures arrive 25 times each second, it multiplies the movement by 25 to estimate meters per second.

Then it smooths bumpy dots. If a dot suddenly jumps impossibly far, the jump is rejected instead of counted as a super-fast run.

Technical view

For position p_i and frame rate f, the raw step and speed are:

step_i = ||p_i - p_(i-1)||speed_i = step_i * fAt 25 FPS, one meter between adjacent frames would imply 25 m/s before quality filtering.

The implementation applies a three-frame median filter, then a centered degree-two Savitzky-Golay filter separately within each finite segment. It differentiates the smoothed positions for velocity and smoothed speed.

What happens to bad or missing data?

  • Missing samples remain missing.
  • Gaps are never bridged by invented motion.
  • The first sample of a segment has no derivative.
  • Player speeds over 14 m/s are rejected by default.
  • Ball speeds over 50 m/s are rejected by default.
  • The rejected step and the derivative touching it are removed.
  • Distance is cumulative accepted step distance only.

The centered filters use future samples, so the pipeline is offline rather than live.

07 / Possession

How does the program decide who controls the ball?

It does not choose the nearest player instantly. It asks whether proximity and motion stay believable long enough.

Fifth-grade view

Being closest to the ball for one picture is not enough. A player must be close for several pictures. Two players close together means the computer says the ball is contested instead of picking a winner too quickly.

Technical view

The detector computes player-ball distance and relative velocity at every frame. Acquisition needs five consecutive frames within 2.5 m. Existing ownership has hysteresis: it can retain control within 3.5 m.

RuleDefaultReason
Acquire radius2.5 mRequires close contact evidence.
Retention radius3.5 mPrevents flicker around the boundary.
Persistence5 framesRejects one-frame coincidences.
Contested margin0.5 mDoes not force a close call.

Possible frame states

controlled

A persistent owner is accepted.

candidate

Someone is close but not confirmed.

contested

Two players are similarly close.

unknown

Ball position or motion is unavailable.

out_of_play

Ball is outside 0..105 by 0..68 m.

free

Ball is usable but no owner is accepted.

Control confidence is a proximity-derived score, not a calibrated probability. Unknown time is reported separately instead of being silently assigned to a team.

08 / Transfers

How is a pass calculated?

MatchMind calls these observable transfer candidates. That wording matters: geometry can show a ball moving between controlled players, but not always the player's intention.

Fifth-grade view

The program waits for a player to control the ball. Then it checks that the ball travels on its own for a little while. Finally, it waits for someone to control it again. If the new player is on the same team, it is a completed transfer. If the other team gets it, it is an interception candidate.

Technical view

detect_passes() is a state machine. It remembers the last controlled owner, opens a pending flight when control is lost, and closes that flight when a persistent receiver is observed.

1. Sender

Record the last controlled player and team.

2. Flight

Require independent frames, displacement, and speed.

3. Receiver

Confirm the next controlled player and compare teams.

outcome = completedReceiver exists and receiver team equals sender team.
outcome = interceptedReceiver exists and receiver team differs from sender team.
Default gateValueWhat it prevents
Minimum independent flight3 framesDirect ownership flips being called passes.
Minimum straight distance3 mTiny position noise becoming a transfer.
Minimum peak speed3 m/sStationary or barely moving ball events.
Timeout8 secondsIndefinite pending flights.

A player recovering their own ball is not a pass. Missing intervals terminate the attempt rather than creating a completed pass across the gap. A transfer can be a clearance, tackle, interception, or loose ball.

09 / Transfer quality

How is transfer difficulty calculated?

This is an inspectable geometry score, not a trained probability model.

Fifth-grade view

A long pass with defenders near the path is considered harder than a short pass into open space. The computer adds points for different kinds of difficulty.

Technical view

The score uses the realized start and end points, the configured attack direction, opponent positions at launch, and opponent positions at arrival. Each component is exported so the result can be audited.

ComponentMaximum
Distance35
Positive progression10
Defenders in interior lane25
Nearest target defender pressure20
Sender pressure10

Critical interpretation

The endpoint is the actual detected reception, so the score describes what happened after the fact. It cannot be a clean release-time prediction because it uses realized target geometry.

!
Not a probability

heuristic_completion_score_0_1 = 1 - difficulty / 100 is a descriptive inverse score. It is not a 25% or 80% chance of completion.

If a defender is missing, quality is marked unavailable rather than assuming the pass was easy.

10 / Shots

How does the shot detector work?

It searches for a fast, independent ball trajectory that points toward a nearby goal.

Fifth-grade view

The program asks: Is the ball moving quickly? Is it going toward a goal? Is it close enough to reach the goal soon? Does the path cross near the goal opening? If the pattern lasts long enough, it marks a possible shot.

Technical view

The detector checks speed, direction, goal distance, horizontal velocity, projected goal-line crossing, time to goal, and persistence. If the recent controlling team is known, the ball must travel in that team's attack direction.

Speed

At least 8 m/s by default.

Geometry

Within 35 m and projected near the goal mouth.

Timing

Projected arrival within 3 seconds.

t_goal = (goal_x - ball_x) / velocity_xThen the detector projects y at the goal line and checks whether it is near the 7.32 m goal mouth centerline, with a configured margin.

Estimated 2D post-shot ball speed comes from a short 1.2-second window; it is not measured strike velocity. Missing positions truncate that window. A confirmed reception stops it so a later kick does not leak into the first shot.

The pipeline also creates separate BAS reference windows. A BAS shot reference does not create a trajectory candidate.

11 / Checking the guesses

How does validation work?

References help compare timing and identity. They do not magically turn an estimate into ground truth.

One-to-one matching

One computer guess cannot claim the same official label twice. The matcher pairs predictions and references only once and reports the leftovers.

The validator builds a cost matrix from timing differences, rejects pairs outside the tolerance, optionally requires actor agreement, and applies Hungarian assignment.

valid pair = abs(prediction_frame - reference_frame) / fps <= 1.0

Unmatched predictions are false positives. Unmatched references are false negatives.

Why BAS is not independent

The supplied ball path is reconstructed using BAS event anchors. Therefore, matching a detector to BAS can show timing consistency, but it is not evaluation against an independently measured ball trajectory.

ValidationExtra requirement
Pass familyTiming and sender actor agreement.
ShotTiming only; shooter identity is not independently verified.
12 / From metrics to explanations

What does the intelligence layer add?

It creates a stable language layer over existing analytics. It does not re-run the detectors.

Fifth-grade view

The analytics make notes like, "the ball changed owners here." Intelligence turns those notes into organized event cards and short explanations. Gemini can choose which approved sentence is most useful, but it cannot invent a new story.

Technical view

build_events() adapts possession, transfer, shot, BAS, speed, and distance results into closed Pydantic event schemas. Each event has a stable content-derived ID, source, significance, identity namespace, validation state, and metrics.

Context windows

ContextBuilder.at(timestamp, window) supports 15, 30, and 60 seconds. It reports current possession, streak, team percentages, unknown ownership, transfers, sequences, fastest players, ball displacement, progression, BAS actions, shot candidates, and limitations.

Commentary selection

The service filters significant events, groups related events, applies cooldowns, and requests one to three sentence IDs per mode. It generates beginner, fan, and analyst options ahead of time, so the browser does not need a network request while you scrub.

Gemini boundary

Gemini receives structured facts and a sentence catalogue. Strict validation rejects unknown IDs, extra fields, and free-form prose. The final text comes from deterministic templates.

Why make the model choose instead of write?

  • It limits unsupported identities and statistics.
  • It keeps uncertainty language attached to estimates.
  • It makes cached output reproducible.
  • It prevents credentials from entering prompts or reports.
  • It keeps analytics deterministic when commentary is disabled.

The tactical engine now contributes closed tactical states and tactical events to the same intelligence context. Commentary can describe supported shape, pressure, formation, and network facts, but it cannot invent tactical intent or causal claims.

The default provider is none, so ordinary runs and tests make no network calls.

13 / New tactical branch

How does the tactics engine work?

This branch adds deterministic tactical evidence without changing the existing ownership, transfer, difficulty, shot, or renderer calculations.

Fifth-grade view

The computer takes a team picture five times each second. It measures how wide and deep the team is, whether the team is defending near or far from its goal, who is close to the ball carrier, and which players are in front of the ball.

It waits before announcing a change. A team that briefly stretches for one picture does not instantly become a new tactical shape.

Technical view

src/tactics/engine.py samples every 200 ms by default. It consumes raw metric recording positions, confirmed ownership, GSR actor labels, and the analytics attack direction. It publishes closed TacticalState objects and persistent tactical events.

Shape

Outfield centroid, width, depth, RMS compactness, pairwise spread, longitudinal position.

Block

Low, mid, or high defending band from centroid distance to own goal.

Pressure

Observed nearby defenders plus backward closing velocity.

What stays unknown?

Unknown is an intentional output. If the goalkeeper role is unavailable, the outfield shape and formation are withheld rather than guessed. If too few players are usable, shape is unavailable. If the carrier, ball, or backward history is missing, pressure is unavailable.

Goalkeepers are excluded from team shape, formation, and ball-relative counts. They remain included in local pressure because a goalkeeper can challenge a carrier.

!
Geometry is not intent

These facts can describe observed positions and movement. They do not prove a coach's instruction, collective intent, or that pressure caused a turnover.

Shape, width, depth, compactness, and spread

For usable outfield points, the centroid is the mean position. Width is max(y) - min(y); depth is max(x) - min(x); compactness is the RMS distance from each player to the centroid; spread is the mean pairwise Euclidean distance. All are in meters.

Shape requires a minimum usable outfield roster. More than ten observed outfield players is treated as ambiguous rather than accepted as a larger shape.

Defensive block bands

While the team is defending, the outfield centroid's distance from its own goal is compared with configurable bands. By default, low is at most 35 m, high is at least 70 m, and the space between is mid. A candidate must persist for three seconds. Missing evidence or unknown ownership resets the state.

Pressure and closing velocity

Local pressure counts opponents within 3 m, 5 m, and 8 m. Closing velocity uses only a backward one-second displacement history; centered future-looking velocities are deliberately not used here. For defender-carrier vector r, closing speed is -(v_defender - v_carrier) dot (r / ||r||). A pressure candidate needs at least two local defenders, one observed closing defender, and enough observed defenders. Two seconds of same-carrier evidence produces sustained pressure.

Static proximity alone is never labeled pressing. Missing defenders make counts lower-bound observations, not full-team certainty.

Ball-relative counts

For an attacking player, the signed longitudinal value is (player_x - ball_x) * attack_direction. Values beyond 0.5 m are ahead or behind; values inside the tolerance are level. The engine separately counts goal-side defenders and keeps availability counts.

Formation estimate

Formation is a conservative longitudinal line-count fit over a trailing 15-second window. It tests 4-3-3, 4-4-2, 4-2-3-1, and 3-5-2. It requires ten identity-stable outfield players, known goalkeeper exclusion, enough coverage, line gaps, a maximum RMSE of 4.5 m, a best-fit margin of 1 m, and at least 80% membership stability. The fit must persist for five seconds. Otherwise the estimate is unknown.

This is not verified lineup information. It does not invent winger or defender roles, and averaging can hide rotations.

Transfer network

The network aggregates completed observable transfers into directed sender-to-receiver edges. It reports counts, distance/progression/difficulty summaries, long-transfer counts, and BAS release/sender support. The default report shows a trailing 60-second network at the current time; a whole-recording option intentionally includes later transfers.

14 / New validity branch

How is projection quality audited?

The new audit measures the unchanged MOT fallback in more detail. It diagnoses the projection; it does not silently repair it.

Fifth-grade view

The computer compares two ways of placing the same player on the field: the normal camera-picture method and the GSR field-coordinate method. It checks where the errors happen and whether changing the clock or flipping the field fixes them.

If a correction makes the old examples look better but has not been tested on new evidence, it could hide the problem. So the audit reports the problem and leaves the working method alone.

Technical view

src/vision/projection_evaluation.py reproduces the existing MOT-foot projection against synchronized GSR using all finite paired detections. It reports global statistics, per-player results, pitch and image grids, boundary regions, landmark-distance bins, triangle shapes, synchronization shifts, orientation experiments, and supplementary image-foot diagnostics.

error_i = ||projected_MOT_i - GSR_pitch_i||Coverage is finite paired samples divided by all eligible detections, including failures.

What experiments are included?
  • Per-player and per-frame error statistics.
  • Pitch boundary and image-region comparisons.
  • Distance to nearest calibration landmark.
  • Triangle simplex and triangle-aspect bins.
  • Synchronization shifts from -2 to +2 frames.
  • Original, x-reversed, y-reversed, and both-reversed orientations.
  • Nearest-actor agreement checks.
  • Actual paired-detection heatmaps with empty cells left blank.

The audit does not subtract the mean error, refit calibration, change the offset, or replace actor mappings. Such changes would optimize in-sample agreement without independent ground contacts. GSR remains primary for all renderer positions; the projection is a fallback and comparison source.

14 / Why it is built this way

Implementation choices and tradeoffs

These choices make the system more auditable, but they also define what it cannot claim.

GSR-first coordinates

GSR pitch coordinates already share a metric convention with the ball, so they are preferred for proximity and motion. MOT projection remains available for comparison and gaps.

Missingness over invention

Unknown ball samples, calibration misses, and broken observation segments remain unknown. The pipeline avoids silently adding distance, speed, ownership, or shots.

Centered smoothing

Centered median and Savitzky-Golay filters reduce quantization noise. The tradeoff is that they use future frames, so the pipeline is explicitly offline.

State machines over instant labels

Possession and transfers require persistence. This reduces flicker and false events, but brief touches can be missed.

Closed intelligence schemas

Pydantic models reject extra fields and invalid values. This creates a stable contract and limits unsupported narration.

Standalone reports

Plots and browser review are generated as static files. No server is needed, but live collaboration and server-side querying are outside the current design.

17 / Keep these words straight

Glossary

Search the terms when the names start to blur together.

MOT
Multiple Object Tracking. A temporary track identity that helps connect a player across video frames. It is not automatically a jersey number.
GSR
The repository's global scene annotation source containing player image boxes, pitch coordinates, actor IDs, and team sides.
BAS
The action annotation source containing labels such as PASS, SHOT, GOAL, and TACKLE, timestamped in the released half-video clock.
Homography
A projective mapping often used to flatten a planar view. MatchMind retains a homography loader but actively uses piecewise triangulation for the panoramic image.
Delaunay triangulation
A way to divide the calibration points into triangles so a local mapping can be applied around each query point.
Barycentric coordinates
Three weights describing where a point lies inside a triangle. MatchMind reuses those weights on the matching pitch triangle.
Observed
A coordinate sample exists and is finite. It may still be rejected for motion quality.
Usable motion
A sample/step survives the speed quality gates and can contribute to accepted speed or distance.
Recording-local time
Time measured from the beginning of the selected clip or half. Add the source offset to recover half-video time.
Transfer
An observable sender-to-receiver ball movement. It is intentionally broader than the word pass.
Independent flight
A period where the ball is moving without a confirmed controlled owner, used to distinguish transfers from direct ownership changes.
Heuristic
A transparent rule-based estimate. It can be useful without being a calibrated probability or official label.
Ground truth
An independently verified reference. The current BAS comparison is not fully independent because ball reconstruction uses BAS anchors.
Tactical state
A sampled, closed record of observed team geometry, phase, block, pressure, ball-relative counts, and formation evidence.
Shape
Outfield geometry summarized by centroid, width, depth, compactness, spread, and orientation-aware longitudinal position.
Closing velocity
Backward relative motion projected toward the carrier. It requires a complete trailing history and is distinct from simply being nearby.
Formation estimate
A conservative longitudinal line-count fit over a trailing window. It is unknown when roster, fit, stability, or persistence gates fail.
Transfer network
A directed aggregation of completed observable transfers. It is not an official passing network or proof of tactical causation.
Pre-event evidence
The latest tactical sample strictly before an original release or start frame, kept separate from later confirmation and realized-target geometry.
Validity audit
A reproducible measurement of the unchanged MOT projection against GSR across regions, offsets, orientations, and paired samples.
No glossary term matches that search.
18 / Honest boundaries

What should you be careful about?

  • Ball positions are event-interpolated and have no height.
  • Ball speed is a 2D estimate, not measured strike speed.
  • MOT IDs are not verified jersey numbers.
  • Synchronization and calibration can introduce errors.
  • Possession is inferred from proximity, motion, and persistence.
  • Transfers can be interceptions, tackles, clearances, or loose balls.
  • Difficulty uses a realized endpoint and is not completion probability.
  • Shot candidates can be false positives or false negatives.
  • Goalkeeper fallback assignment is geometric and can be ambiguous.
  • Tactical shape and formation are geometric estimates, not verified tactics or lineups.
  • Pressure is observed proximity plus closing evidence, not proof of pressing intent or causation.
  • Validity-audit disagreement is relative to GSR, not independently surveyed absolute error.
  • Centered smoothing uses later frames and is not causal.
